# ADR-0008: Correctness is defined by flowcast-generated goldens and invariants

- Status: accepted
- Date: 2026-09-24
- Supersedes: ADR-0007

## Context

flowcast used to take byte-for-byte agreement with another implementation as the
definition of correctness, and compared every intermediate step of the engine too: the
parsed table, text sizes, the row and column of each element, wire styles, the track of
each segment. That approach caught every divergence, but it also locked in the engine's
internal structure. Changing how rows are split or how tracks are assigned turned a
large number of tests red, even when the output file was still correct or better. Every
intentional behavior change also had to be recorded in an exception list.

## Decision

Correctness has two parts, both looking only at the output:

1. Goldens generated by flowcast itself for each case: the .drawio file, the findings
   report (table issues, engine warnings, self-check results), diagrams in the other
   directions, and CLI session transcripts. Goldens may only change through the -update
   flag, and whoever changes them must look at the images and read the diff.
2. Invariants run over every valid case:
   - the geometry self-check reports no errors;
   - merging onto a freshly generated, unedited file does not change the file;
   - wires into a condition attach at the top, wires out leave only from the left,
     right or bottom;
   - the other directions are axis-swapped or flipped images of the top-down direction.

Each package's unit tests may still check details internal to that package. No test
outside a package may compare the engine's intermediate state.

## Consequences

- Restructuring the engine while keeping the output unchanged turns no test red.
- An intentional behavior change is one -update run and one golden diff to read. There
  is no exception list anymore.
- Goldens do not prove themselves correct. The invariants and the reviewer looking at
  the images are the two things that keep goldens from drifting.
