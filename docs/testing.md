# Testing

This document is for someone preparing to commit a change to flowcast. After reading
it, you know which checks to run, when goldens must be regenerated, how to add a case,
and how to tell whether the test suite actually catches bugs.

It is best to read [structure.md](structure.md) first to learn the packages and
directories.

## What decides that a change is correct?

Correctness looks only at flowcast's output (ADR-0008):

- **Goldens.** Each case in the case suite has a .drawio file and a report file
  generated by flowcast itself. The report file lists the table issues, the engine
  warnings and the self-check results, each with its code. There are also goldens for
  the other directions, and transcripts of command line sessions: the command run,
  every printed line, the exit code, and the fingerprint of each generated file.
- **Invariants.** Conditions every diagram must satisfy, checked on every valid case:
  - the geometry self-check reports no errors;
  - merging onto a freshly generated, unedited file does not change the file;
  - wires into a condition attach at the top, wires out leave only from the left,
    right or bottom;
  - the other directions are axis-swapped or flipped images of the top-down direction.

Unit tests in each package may check details internal to that package. No test outside
a package may compare the engine's intermediate state, so restructuring the engine
while keeping the output unchanged turns no test red.

## Which checks to run before committing?

```
sh tools/check.sh
```

The script checks gofmt, runs go vet, then runs the whole go test suite. On a machine
with the drawio CLI it also runs a check that the real draw.io draws wires at the right
coordinates on a few cases.

Before a large layout change, also run the end-to-end acceptance check. It builds every
case in every direction, then has the real drawio draw them and compares each wire; it
takes a few minutes:

```
DIRS="TD BT LR RL" sh tools/accept.sh
```

## When must goldens be regenerated?

When a change intentionally changes the output: layout, styles, messages, lines printed
by the command line. Change the code first, then regenerate:

```
go test ./conformance -update      # .drawio goldens, reports, direction goldens
go test ./cmd/flowcast -update     # command line transcripts
```

Then read the golden diff, and open the images of the diagrams that changed, for
example with flowcast build and the --png flag. Only commit when every change is one
you meant to make. A golden that changed without anyone looking at it is a behavior
that changed without anyone knowing.

Running go test ./conformance -update when a change was not meant to change the output
but the tests are still red is wrong: what needs fixing is the code, not the goldens.

## How to add a case?

1. Write the table into conformance/cases, named after the algorithm branch it pins
   down, not after its business content. 25-tracks-parallel.md, not
   25-order-flow.md. Deliberately invalid tables get numbers starting with 9 and only
   have a report golden, no .drawio.
2. Keep the table as small as possible while still forcing the branch to pin down.
3. Generate the goldens, look at the image, read the report.
4. Run mutation testing (section below) to confirm the new case kills the mutation it
   targets. A case added because someone thought it reaches some branch, but that
   kills no mutation, is a useless case.

Machine-found cases (number 60 and above, content like "A-1 x", "d0") keep their
content unchanged: changing the text changes box widths, and can make the case stop
killing its mutation.

Diagrams without lanes go in conformance/flowchart, mermaid diagrams in
conformance/mermaid. Merge scenarios (a table together with an old, manually edited
.drawio file) go in conformance/merge and are run through the command line transcripts.

## How to tell whether the test suite catches bugs?

```
sh tools/mutate.sh                 # every mutation
ONLY=layout/ sh tools/mutate.sh    # only mutations in one directory
```

The script deliberately breaks one place in the code at a time, runs go test, then
restores it. A mutation that leaves the tests green is a place the test suite does not
guard. The working tree must be clean before running, because the script restores with
git checkout.

Each missed mutation is handled in one of the following ways:

- Add a case that makes that bug show up in the output.
- Prove that the mutation never changes the output, then record the reason in the list
  of equivalent mutations at the top of the script, and remove it from the run list.

Add a new mutation for every new rule introduced into the engine. The target string
must appear exactly once in the file, and should avoid alignment whitespace because
gofmt realigns columns.

Some lessons for designing cases for the placement phase:

- Whether a face already has a horizontal arrow only affects the column of a side
  branch when the horizontal arrow is placed before the side branch, meaning the
  cross-lane target must come first in the table.
- The choice of which source to use as the reference for a merge node only shows up
  when the sources are in different columns and have no common branching node.
- To force a side branch to drift across several blocked cells, use a horizontal arrow
  to another lane: it blocks every positive column of the source lane on the same row.

## What are the vector files?

The conformance directory has a few JSON files holding inputs and expected results for
the parts that need checking over very many values: number rounding, csv reading,
encoding decoding, XML reading and writing, reading numbers and base64 in old .drawio
files, measuring and wrapping text, self-check on broken geometry, and render checking
on real SVG exported by drawio. The unit tests of the corresponding package read them.

They are fixed regression data. When intentionally changing a behavior that a vector
pins down, fix the expected result in the corresponding file and record the reason in
the commit.

## Measuring layout quality

```
go run ./tools/metrics conformance/mermaid/*.mmd conformance/flowchart/*.md
```

Prints for each diagram: the number of wires of each style, the number of waypoints,
the number of places where two wires cross, the total wire length, the size, the number
of self-check findings, and the ratio of main path edges drawn straight. Use it to
judge a heuristic by numbers rather than by feel: run it before and after a change and
compare.

## Regenerating the font measurement table

```
go run ./tools/extractmetrics /path/to/Verdana.ttf data/verdana.json
```

Only needed when changing the font. Changing the table changes the size of every box,
so afterwards every golden must be regenerated and the images reviewed.
